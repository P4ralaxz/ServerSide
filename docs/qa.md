# คำถามที่อาจโดนถาม — แยกตามคน

ตอบสั้น 2–3 ประโยค: **คำตอบ → เหตุผล → (ถ้าถูกถามต่อ) ชี้ที่โค้ดหรือเทส**
คำถามที่ไม่ใช่ส่วนของตัวเอง ให้ส่งต่อคนที่รับผิดชอบ: "ขอให้ 670700xx ตอบส่วนนี้ครับ"
ไม่รู้คำตอบ → "ขอเช็คแล้วตอบหลังนำเสนอครับ" ดีกว่าเดา

## 67070017 — login, กันแจ้งซ้ำ, สิทธิ์

**ทำไมไม่มีรหัสผ่าน ปลอดภัยกว่าจริงไหม**
ไม่มีรหัสผ่านก็ไม่มีรหัสผ่านให้รั่วหรือให้ลืม นักศึกษาทุกคนมีอีเมล KMITL อยู่แล้ว รหัส 6 หลักอายุ 10 นาที ใส่ผิดเกิน 5 ครั้งรหัสนั้นใช้ไม่ได้ และจำกัดจำนวนครั้งต่อ IP (429)

**เก็บรหัส OTP ยังไง ทำไมใช้ HMAC ไม่ใช้ hash ธรรมดา**
เก็บเป็น HMAC-SHA256 ที่ใช้ secret ของเซิร์ฟเวอร์ (`otp.service.ts`) รหัส 6 หลักมีแค่ล้านแบบ ถ้าใช้ hash ธรรมดา คนที่ได้ฐานข้อมูลไปไล่ hash ครบล้านแบบได้ในไม่กี่วินาที แต่ HMAC ต้องรู้ secret ด้วย และตอนเทียบใช้ `timingSafeEqual` กันการวัดเวลา

**ทำไม `request-code` ตอบ 202 ข้อความเดียวกันทุกครั้ง**
ถ้าตอบต่างกันระหว่างอีเมลที่มีกับไม่มีในระบบ คนนอกจะไล่เช็คได้ว่าใครมีบัญชี

**ทำไม JWT มีแค่ `sub` ไม่ใส่ role**
ถ้าใส่ role ไว้ใน token แล้วเราเปลี่ยนบทบาทหรือระงับบัญชี token เก่ายังใช้ได้จนหมดอายุ (8 ชม.) Guard ของเราโหลดผู้ใช้จากฐานข้อมูลทุก request และเช็ค `is_active` กับ `deleted_at` ระงับแล้วมีผลทันที แลกกับ 1 query ต่อ request

**กดแจ้งพร้อมกันสองคน จะได้ 2 ใบไหม**
ไม่ได้ ฐานข้อมูลบังคับด้วย partial unique index `idx_tickets_asset_open` — ครุภัณฑ์ชิ้นหนึ่งมีใบที่สถานะยังเปิดอยู่ได้ใบเดียว คนที่สองชน unique violation (23505) ซึ่ง `DbErrorFilter` แปลงเป็น 409 ถ้าเช็คแค่ในโค้ดด้วย SELECT ก่อน INSERT สองคำขอจะผ่านการเช็คพร้อมกันได้ (race condition)

**ทำไมเป็น partial index ไม่ใช่ unique ธรรมดา**
ของชิ้นเดียวเสียได้หลายครั้งในชีวิต ใบที่ปิดแล้วต้องไม่นับ index จึงมี `WHERE` เฉพาะสถานะที่ยังเปิด และมี contract test เทียบว่าเงื่อนไขนี้ตรงกับ `OPEN_STATUSES` ในโค้ด

**แจ้งหลายชิ้นในครั้งเดียว ถ้าบางชิ้นซ้ำทำยังไง**
ใช้ `INSERT … ON CONFLICT … DO NOTHING` ชิ้นที่ซ้ำถูกข้ามและส่งกลับใน `skipped[]` ได้ 201 ถ้าซ้ำทุกชิ้นได้ 409 ไม่ใช้ try/catch เพราะ Postgres abort ทั้งทรานแซกชันทันทีที่เจอ unique violation

**ทำไมคนห้องอื่นได้ 403 ไม่ใช่ 409**
เราเช็คตามลำดับ บทบาท (403) → เป็นเจ้าของ/พักห้องนั้น (403) → สถานะ (409) ถ้าเช็คแจ้งซ้ำก่อน คนห้องอื่นจะได้ 409 แล้วรู้ว่าห้องนั้นแจ้งอะไรไว้ ข้อมูลรั่วผ่าน error

**ลิงก์ใน QR เดาได้ไหม**
ไม่ได้ ใช้ `qr_token` สุ่ม 128 บิต (`randomBytes(16)`) ไม่ใช่รหัสครุภัณฑ์ที่ไล่เลขได้

## 67070053 — workflow, สิทธิ์ของแต่ละบทบาท

**ทำไมแยก endpoint `/assign` `/status` `/confirm` ไม่ใช้ `PUT /tickets/:id` ตัวเดียว**
แต่ละการกระทำมีคนที่ทำได้ไม่เหมือนกัน และต้องการข้อมูลไม่เหมือนกัน แยก endpoint แล้วแต่ละตัวมี Guard และ DTO ของตัวเอง ไม่ต้องเขียน if ซ้อนว่าใครแก้ฟิลด์ไหนได้ และ Swagger อ่านเข้าใจง่าย

**ถ้าสองคนเปลี่ยนสถานะใบเดียวกันพร้อมกัน**
ทุกการเปลี่ยนสถานะทำในทรานแซกชันเดียว: lock แถวด้วย `pessimistic_write` (SELECT … FOR UPDATE) → UPDATE → INSERT ประวัติ คนที่สองต้องรอ พอได้ lock ก็เห็นสถานะใหม่แล้ว ถ้าเปลี่ยนต่อไม่ได้ก็ได้ 409 มีเทส `workflow-concurrency` ยิงพร้อมกันจริง

**เก็บสถานะที่ไหน ถ้าจะเพิ่มขั้นใหม่ต้องแก้กี่ที่**
`src/domain/status-rules.ts` ไฟล์เดียว บอกว่าขั้นไหนไปขั้นไหนได้ ใครทำได้ service ทุกตัวอ่านจากที่นี่ ไม่มีเงื่อนไขซ้ำกระจายในโค้ด

**`ticket_status_logs` กับ `ticket_audit_logs` ต่างกันยังไง**
status log เก็บเฉพาะการเปลี่ยนขั้นจริง ใช้คิดเวลาค้างต่อขั้นในรายงาน ส่วนการกระทำที่ไม่เปลี่ยนขั้น เช่น มอบหมายซ้ำ เลื่อนนัด เปลี่ยนความด่วน ไปเก็บใน audit log รายงานเวลาจึงไม่เพี้ยน

**ทำไม Staff ยืนยันใบห้องพักแทนไม่ได้**
คนที่รู้ว่าซ่อมหายจริงคือคนที่อยู่ห้องนั้น ถ้าให้ Staff ปิดแทน ก็กลับไปเป็นปัญหาเดิมที่ปิดใบทั้งที่ยังไม่หาย ใบส่วนกลางไม่มีเจ้าของห้อง Staff จึงเป็นคนยืนยัน และถ้าไม่มีใครยืนยันใน 3 วัน ระบบปิดให้

**สิทธิ์ยืนยันผูกกับคนแจ้งหรือกับห้อง**
กับห้อง ใครที่พักห้องนั้นตอนนี้ยืนยันได้ (เดโมให้รูมเมทเป็นคนปิด) เพราะคนแจ้งอาจย้ายออกไปแล้ว

**ความเห็นภายในกันไม่ให้นักศึกษาเห็นยังไง**
กรองที่ API ไม่ใช่ซ่อนที่หน้าเว็บ ใช้เงื่อนไขเดียว `TicketPolicy.canSeeInternal` ทั้งตอนอ่านและตอนเขียน นักศึกษาส่ง `is_internal: true` มาได้ 403

**ปุ่มบนหน้าเว็บรู้ได้ยังไงว่าควรโชว์ปุ่มไหน**
API ส่ง `actions` มากับใบ คำนวณจาก status-rules + TicketPolicy ชุดเดียวกับที่ตรวจตอนกด หน้าเว็บไม่มีกฎของตัวเอง ต่อให้ยิง API ตรงก็ถูกตรวจซ้ำ

**ownership ทั้งหมดอยู่ที่ไหน**
`TicketPolicy` ที่เดียว ทั้ง "แตะได้" และ "เห็นได้" แก้คู่กันเสมอ ไม่งั้นจะมีกรณีที่กดได้แต่มองไม่เห็น หรือเห็นแต่ไม่ควรเห็น

## 67070097 — กฎอัตโนมัติ, รายงาน, สแตก, การทดสอบ

**ทำไมเลือก NestJS ไม่ใช้ Express เปล่า ๆ**
NestJS มีโครงสร้างโมดูล, DI, Guard, Pipe, Filter ในตัว กฎสิทธิ์และ validation จึงอยู่เป็นที่เป็นทาง และ decorator ของ Swagger อยู่ติดกับ controller เอกสารไม่หลุดจากโค้ด

**ทำไมใช้ PostgreSQL**
กฎสำคัญต้องการความสามารถของ Postgres: partial unique index, CHECK, trigger, row lock และ `ON CONFLICT` ให้ฐานข้อมูลบังคับกฎเอง ไม่ใช่พึ่งโค้ดอย่างเดียว

**ทำไมปิด `synchronize` ของ TypeORM**
`synchronize: true` สร้างตารางจาก entity ได้ก็จริง แต่ partial index, trigger, view และ CHECK จะหายไปเงียบ ๆ เราจึงเขียน migration เป็น SQL ล้วน และรันด้วย `npm run migration:run`

**cron ปิดอัตโนมัติ ถ้าเซิร์ฟเวอร์ล่มตอนครบ 3 วันพอดี**
รอบถัดไปก็ปิดให้ เพราะเงื่อนไขคือ "รอยืนยันนานกว่า 72 ชม." ไม่ใช่ "ครบพอดีตอนนี้" และก่อนปิดแต่ละใบจะ lock แถวแล้วเช็คซ้ำ (`closeIfStillDue`) ถ้าระหว่างนั้นผู้พักกดยืนยันหรือมีคนแย้งพอดี ใบนั้นจะไม่ถูกปิด

**ถ้ามีเซิร์ฟเวอร์หลายตัว cron รันซ้ำกันไหม**
รันซ้ำได้แต่ไม่ปิดซ้ำ เพราะทุกใบถูก lock และเช็คสถานะใหม่ก่อนปิด ตัวที่มาทีหลังเจอว่าใบปิดไปแล้วก็ข้าม

**ปุ่ม `/admin/jobs/auto-close/run` เป็นช่องโหว่ไหม**
เรียกได้เฉพาะ admin (staff ได้ 403) ใช้ฟังก์ชันเดียวกับ cron ไม่มีพารามิเตอร์ข้ามเงื่อนไข มีไว้เพราะตอนนำเสนอรอ 3 วันไม่ได้

**รายงาน "ไม่นับช่วงรออะไหล่" คิดยังไง**
คิดจาก `ticket_status_logs` ว่าแต่ละใบอยู่แต่ละขั้นนานเท่าไร แล้วหักช่วงที่อยู่ขั้น `pending_parts` ออก (`reports.service.ts`) ทุก query มี `deleted_at IS NULL` และจัดกลุ่มตามเวลาไทย

**เวลาใช้ timezone อะไร**
เก็บเป็น `timestamptz` ทุกคอลัมน์ process ตั้ง `TZ=UTC` ส่วนปี พ.ศ. ในเลขใบคิดตามเวลาไทยผ่าน `common/time/thai-year.ts` ที่เดียว ใบที่แจ้งตอนตี 1 คืนปีใหม่ไทยจะได้เลขปีถูก

**ทำไมเทสบน Postgres จริง ไม่ใช้ mock หรือ SQLite**
กฎหลักอยู่ในฐานข้อมูล (partial index, lock, trigger) ถ้าใช้ mock หรือ SQLite เทสจะผ่านทั้งที่ของจริงพัง Testcontainers เปิด Postgres 16 ใน Docker ให้ทุกครั้งที่รัน

**mutation testing คืออะไร**
แกล้งแก้โค้ดให้ผิดกฎทีละข้อ เช่น ให้ช่างปิดใบได้ ข้ามการเช็คความเป็นเจ้าของ เอาเงื่อนไข index ออก แล้วรันเทส ถ้าเทสยังเขียว แปลว่าเทสไม่ได้ป้องกันกฎข้อนั้นจริง เราทำ 24 แบบ เทสแดงทั้ง 24

**808 เคสทดสอบอะไรบ้าง**
unit 83 (สถานะ, สิทธิ์, ตัวช่วย) · API e2e 675 (ทุก endpoint พร้อมกรณีสิทธิ์ สถานะ และกดพร้อมกัน บน Postgres จริง) · หน้าเว็บ 50 (Playwright เดินทุกบทบาท รวมขั้นเดโมทั้ง 12 ขั้น)

**Soft delete ทำยังไง**
ลบด้วยการตั้ง `deleted_at` ไม่ลบแถวจริง ประวัติใบยังอ้างถึงได้ ทุก query รวม raw SQL ของรายงานต้องกรอง `deleted_at IS NULL` เอง เพราะ `@DeleteDateColumn` ไม่กรอง `manager.query()`

**ต่างจากเวอร์ชันแรกที่ทำด้วย Python ยังไง** (ถ้าถูกถาม)
เขียนใหม่ด้วย TypeScript ไม่ได้แปลตรง ๆ แก้ช่องโหว่ที่เจอระหว่างวิเคราะห์ของเดิมไปด้วย เช่น ลำดับการเช็คสิทธิ์ และย้ายการกันแจ้งซ้ำไปให้ฐานข้อมูลบังคับ เทสเดิม 252 เคสแปลมาแล้ว 241 เคส ที่เหลือเป็นฟีเจอร์ที่ตัดออกโดยตั้งใจ (`test/PARITY.md`)
